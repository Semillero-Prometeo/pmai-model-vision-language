1. Nueva arquitectura de LLM

El sistema reemplaza Ollama por un router que selecciona automáticamente el backend según conectividad.

Pregunta ──▶ Router ──▶ [ ¿OPENAI_API_KEY + internet? ]
                             ├── SÍ ──▶ OpenAI gpt-4o-mini (API)
                             └── NO ──▶ Gemma 4 E2B (GGUF local · 2.9 GB)
Para activar OpenAI: añade OPENAI_API_KEY=sk-... en el archivo .env. Sin clave o sin internet, el sistema usa Gemma automáticamente.

3. Mejoras al prompt (prompt/principal.py)

  • ✓Identidad más precisaR-One se define como robot físico real, no avatar ni chatbot. Se amplían las áreas de competencia (astronomía, filosofía, literatura, cine).
  • ✓Chain-of-Thought en 5 pasosRazonamiento estructurado: Persona → Intención (6 categorías) → Contexto visual → Movimientos → Veracidad.
  • ✓Guía semántica de movimientosLos 34 movimientos ahora están agrupados en 7 categorías con instrucción de cuándo usar cada uno, eliminando selecciones aleatorias.
  • ✓Contexto visual como dato activoEl campo contexto se procesa con la misma prioridad que etiqueta: estado emocional, situación física, idioma.
  • ✓Idioma forzado en 4 puntosLa regla "responde SIEMPRE en español" aparece en: identidad, razonamiento paso 3, anotación del campo y bloque de reglas. Cubre preguntas, etiquetas y contextos en inglés.
  • ✓Temas delicadosNueva categoría tema_delicado con regla de neutralidad estricta para política, religión y controversias.
  • ✓Prompt injection explícitaInstrucción directa para ignorar órdenes embebidas en los campos de datos de entrada.
  • ✓9 ejemplos representativosDe 5 a 9 ejemplos: añadidos tema delicado, contexto visual útil, beneficio/opinión y despedida.

4. Bugs corregidos

  • #1
    Formato de chat incorrecto → respuesta vacíaGemma 4 instruction-tuned requiere el formato <start_of_turn>user\n...<end_of_turn>\n<start_of_turn>model\n. Sin él, el modelo no genera nada. El prompt se enviaba como texto plano.
  • #2
    n_ctx=4096 demasiado pequeño → JSON truncadoEl prompt de producción ocupa ~3 169 tokens, dejando solo ~900 para la respuesta. Respuestas largas se truncaban y el JSON quedaba incompleto. Subido a n_ctx=8192.
  • #3
    Singleton con @lru_cache congelaba el n_ctx viejo@lru_cache mantenía la instancia con n_ctx=4096 aunque el código se actualizara. Reemplazado por patrón que crea una instancia fresca por petición.
  • #4
    KV cache lleno tras 2-3 peticiones → modelo mudoreset() de llama-cpp-python solo pone n_tokens=0 pero no libera el contexto de entrada. Tras 2 peticiones el contexto se llenaba. Solución: instancia nueva por petición.
  • #5
    Generación vacía esporádica con temperature=0.7Gemma entra en bucle de sampling vacío con temperatura alta y prompts largos. Añadido sistema de 3 reintentos con parámetros distintos: (0.3, top_p=0.9) → (0.5, top_p=0.95) → (0.2, seed=42).
  • #6
    Token </start_of_turn> como prefijo del JSONA veces Gemma emite ese token antes del JSON. Se limpia con .replace("</start_of_turn>", "") en postprocesado.
  • #7
    JSON con } extra al final → Extra dataEl extractor con rfind("}") tomaba el último } extra que el modelo añade, invalidando el parse. El nuevo extractor recorre los } de derecha a izquierda hasta encontrar un JSON válido.
  • #8
    (Contexto: mujer sonriendo…) literal en respuestas de cachéEl contexto visual se concatenaba textualmente al final de respuestas cacheadas. Eliminado — el contexto solo viaja al LLM vía el prompt, nunca como texto visible.
